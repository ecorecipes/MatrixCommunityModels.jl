Management and decisions

A ManagedCommunity is a closed community with what a decision analysis needs of a model: named parameters (a build function maps the names to vital rates or matrix entries), a management action, and named outcomes. project runs it and returns a ManagedTrajectory. None of this needs a decision package.

An action is plain data, a named tuple:

fieldmeaning
remove = target => fractionremove that fraction of a species or of some of its stages after each step (harvest, cull)
take = target => numberremove that number of individuals after each step, or all there are (a quota)
add = target => numberadd that number after each step (supplementation, a release)
parameters = (; name = value)replace parameter values; a function is applied to the value in force
environment = (t, env) -> env′replace the environment of step t
stepsthe steps after which remove, take and add apply

A target is a species (:prey) or (species, stages), for example (:prey, :adult). The empty tuple (;) is no intervention. Removal acts on the state after a step, as the removal press of MCMState does.

DecisionAnalysis.jl

DecisionAnalysis.jl analyses decisions from the outcomes of a model: payoff tables, decision rules, and the value of information. It reaches a model through four verbs. This package does not depend on it; when both are loaded, the extension MatrixCommunityModelsDecisionAnalysisExt gives the verbs methods:

verbfor a managed community
with_parameters(m, θ)the draw θ, a named tuple, merged into m.parameters
apply_action(m, action)the action set to action ((;) or nothing: none)
simulate(m; rng)project(m; rng)
outcome(run)run.problem.outcomes(run), by default the final abundance of each species

so that outcomes(m, actions, draws; replicates, seed) of DecisionAnalysis.jl runs the community over parameter draws, actions and replicates, with the same seeds under every action (common random numbers). draws is any Tables.jl table with one column per named parameter, for example a named tuple of vectors. A deterministic problem (demographic = false) ignores the seed and gives equal replicates.

DecisionAnalysis.jl needs Julia 1.12 or later; on Julia 1.11 the extension is not loaded and the rest of the package is unaffected. It is not registered: add it, and FiniteKernels.jl which it needs, by URL.

using Pkg
Pkg.add([PackageSpec(url = "https://github.com/ecorecipes/FiniteKernels.jl"),
         PackageSpec(url = "https://github.com/ecorecipes/DecisionAnalysis.jl")])

MatrixCommunityModels.ManagedCommunity — Type
ManagedCommunity(build; parameters = (;), action = (;), outcomes = final abundances,
                 demographic = false)
ManagedCommunity(community, n0, envs; kwargs...)
ManagedCommunity(m::ManagedCommunity; parameters, action, outcomes, demographic)

A closed community with named parameters, a management action and named outcomes: what a decision analysis needs of a model. project(m; rng) runs it and returns a ManagedTrajectory.

Parameters. build(θ) takes a named tuple of parameter values and returns the model at those values as a named tuple with community, n0 and envs (further fields are ignored), which is what the model functions of this package return or nearly so, for example

θ -> (m = predator_prey(merge(BARRAQUAND_GIMENEZ_2019, (adult_survival = (prey = θ.prey_survival,
                                                                         predator = 0.7),)));
      (community = m.community, n0 = m.n0, envs = fill(nothing, 20)))

So the mapping from names to vital rates or matrix entries is build itself, written once and in the open. parameters holds the values in force; names that build does not read are ignored by it. build is called once for every projection, so keep it cheap or memoise it.

The second form is for a community whose responses read their rates from the environment (ctx.env, as the Verde River fish and the ducks do): the parameters are merged into the environment of every step, which must then be a named tuple.

Actions. action is a named tuple with any of the fields below; (;) or nothing is no intervention.

  • remove = target => fraction: remove that fraction of the target after each step, as harvesting or culling would. A target is a species (:prey) or (species, stages) with a stage or group name as understood by stage_total, or a vector of them ((:prey, :adult)). Several removals are a vector of pairs.
  • take = target => number: remove that number of individuals from the target after each step, or all of them if there are fewer, spread over the target's states in proportion to their numbers.
  • add = target => number: add that number to the target after each step (supplementation, a release). A target with several states needs a vector, one number per state.
  • parameters = (; name = value, ...): replace parameter values; a function is applied to the value in force, as in (; fecundity = x -> 0.8x). This is the place for an intervention that changes a vital rate.
  • environment = (t, env) -> env′: replace the environment of step t, for an intervention that acts through it (a designed flow, a bag limit).
  • steps: the steps after which remove, take and add apply (default: every step).

Interventions on the state happen at the census that ends a step, on the state that advance returned, in the order remove, take, add; what was removed and added is recorded by state and time in the result.

Outcomes. outcomes(run) receives the ManagedTrajectory and returns a named tuple of numbers, for example run -> (; prey = abundance(run.trajectory, :prey)[end], harvested = sum(run.removed)). The default is the final abundance of each species, by name.

Chance. With demographic = true the projection has demographic stochasticity (see project) and needs rng; remove then takes each individual with the given probability and take draws individuals without replacement. rng itself only seeds other generators: its first draw seeds the one used by the interventions, and one further draw seeds the generator of each step. These draws are made whatever the action, so two actions projected with generators in the same state meet the same chance: every step starts from the same seed under both, and the species that are stepped before the first one whose state differs draw the same numbers.

The third form copies a problem with some fields replaced. The type is immutable.

MatrixCommunityModels.ManagedTrajectory — Type
ManagedTrajectory

Result of project on a ManagedCommunity: trajectory, the CommunityTrajectory (states after the interventions of each census); removed and added, matrices laid out as trajectory.u, with in row t + 1 what the action removed from and added to each state at time t (row 1, the start, is zero); and problem, the ManagedCommunity that was run. run.trajectory.community.layout[species] gives the columns of a species.

source
MatrixCommunityModels.project — Method
project(m::ManagedCommunity; rng = nothing)

Project a ManagedCommunity: build the model at its parameters (with the action's changes to them), then for each environment in turn advance the community one step and apply the action's interventions to the state. Returns a ManagedTrajectory.

With m.demographic the steps have demographic stochasticity and rng is required; each step draws from a generator of its own, seeded from rng (see ManagedCommunity), so the run is not the one project(community, n0, envs; rng) would give from the same generator. Otherwise rng is not used, the projection is deterministic, and without interventions on the state it is project(community, n0, envs), step for step.

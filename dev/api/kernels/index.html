Integral projection models and kernels

Continuous stages, kernel nets discretised on a mesh, kernels that respond to pools, and weights over a continuous trait.

MatrixCommunityModels.ContinuousStage — Type
ContinuousStage(name, lower, upper, cells)
ContinuousStage(name, domain::ContinuousDomain)

A stage whose individuals differ in a continuous trait (size, say) between lower and upper. The trait is cut into cells mesh cells of equal width. In a net built with kernel_net the stage becomes the stages name1, name2, ..., one per cell, each holding the number of individuals in that cell; name itself stays usable as their total (ctx.n[:plant], stage_total(sol, :thistle, :plant)).

meshpoints(stage) are the trait values at the middle of the cells, step_size(stage) is the cell width and stage_names(stage) are the cell names. In a response, ctx.n[stage] is the vector of numbers in the cells, in the order of meshpoints(stage).

Base.getindex — Method
n[stage::ContinuousStage, stratum]

The numbers of individuals in the cells of stage that are in one stratum of a net made with stratify, in the order of meshpoints(stage): ctx.n[plant, :infected] are the infected plants by size, where ctx.n[plant] are all plants by size. The cells are found by the names stratify gives them (stratum_stage, with its default separator).

source
Base.getindex — Method
n[stage::ContinuousStage]

The numbers of individuals in the cells of stage, one for each cell in the order of meshpoints(stage), read from a stage vector such as ctx.n in a response. (ctx.n[:plant], with the stage's name, is their total.)

The cells are found by name, not by position. The result is therefore right whatever other stages the net holds, and it stays right when the net is refined with stratify or expand_stages: each entry is then the total over the stages that descend from that cell.

MatrixCommunityModels.by_trait — Method
by_trait(stage, f; stratum = nothing)
by_trait(stage, factors; stratum = nothing)

A response value that scales each entry of a transition according to the trait of the individual it comes from: entries leaving the cell of stage at trait value z are multiplied by f(z), and entries leaving other stages are left alone. The factors can also be given as a vector, one for each cell. Return it from a response:

respond(life, :seeding => ctx -> by_trait(plant, z -> exp(-0.02 * eggs_on(z, ctx))))

The response keeps working if the net is refined afterwards with stratify or expand_stages: the cells of every stratum take the factor of the cell they descend from. A response that depends on the stage's own numbers should read them with ctx.n[stage], which finds the cells by name, rather than by position in ctx.n.

A response attached after stratify sees the cells of the strata, so it names the stratum the individuals come from: with stratum, the factor applies to entries leaving the cells of stage in that stratum (the names stratum_stage gives them, with its default separator, as for trait_weights). The stratum they go to is already fixed by the transition the response is attached to. A life cycle can therefore be written for one stratum and its fates split after stratifying:

life = kernel_net(fan, :growing => (y, x) -> survival(x) * growth(y, x))
net = stratify(life, [:healthy, :infected]; coupling = Dict(:growing => [1 0; 1 0]))
net = respond(net,
    :growing_healthy => ctx -> by_trait(fan, x -> 1 - risk(x); stratum = :healthy),
    :growing_healthy_to_infected => ctx -> by_trait(fan, risk; stratum = :healthy))

Entries leaving other stages are left alone, but an entry leaving a cell of stage that is not in stratum (because the stratum is misspelt, belongs to another transition, or the net has no strata) is an error, raised when the response is evaluated.

MatrixCommunityModels.kernel_net — Method
kernel_net(stages, transition => kernels, ...; rule = :midpoint)
kernel_net(stage::ContinuousStage, transition => kernel, ...; rule = :midpoint)

A projection net whose stages may carry a continuous trait: an integral projection model written, like any other life cycle, as named transitions between stages.

stages lists the stages, each a Symbol (an ordinary stage) or a ContinuousStage. Each transition is name => [(from => to) => kernel, ...], the form used by ValuedProjectionNet, where the kernel is

  • between two continuous stages, a function (z′, z) -> density: the density of individuals with trait z′ next time step, per individual with trait z now;
  • from an ordinary stage to a continuous one, a function z′ -> density;
  • from a continuous stage to an ordinary one, a function z -> number;
  • between two ordinary stages, a number.

Between two continuous stages on the same mesh the kernel can also be a PKernel or an FKernel of IntegralProjectionModels.jl (with any eviction correction it carries), whose domain is that mesh; it is discretised there by materialize, which uses the midpoint rule, so rule must be :midpoint.

With a single continuous stage a transition can be written name => kernel.

Kernels are evaluated at the middle of each cell (rule, passed to left_kan_extension, can also be :trapezoidal or :simpson for kernels between continuous stages). Individuals that a kernel sends outside the range of a trait are lost, so the range should be wide enough to hold the population.

A kernel wrapped in responsive is rebuilt each time step from the context; one wrapped in tabulated is interpolated between kernels built at values of a pool. The kernels they return may be any of the above, PKernel and FKernel included.

The continuous stages are kept with the net as its meshes (meshes(net)), so a community that holds the species is solved as a coupled IPM by IntegralProjectionModels.jl (see project).

The result is a responsive projection net, so respond, births, inflow, ⊕, species and the rest apply. by_trait writes a response in terms of the trait and trait_weights a pool contribution.

plant = ContinuousStage(:plant, 0.0, 10.0, 100)
life = kernel_net(plant,
    :growing => (z′, z) -> survival(z) * growth(z′, z),
    :seeding => (z′, z) -> seeds(z) * recruit_size(z′))
with_seed_bank = kernel_net([:seed, plant],
    :dormancy    => [(:seed => :seed) => 0.5],
    :germinating => [(:seed => :plant) => z′ -> 0.1 * recruit_size(z′)],
    :growing     => [(:plant => :plant) => (z′, z) -> survival(z) * growth(z′, z)],
    :seeding     => [(:plant => :seed) => z -> seeds(z)])

MatrixCommunityModels.responsive — Method
responsive(f)

Mark a kernel of kernel_net as depending on the context: f(ctx) is called every time step and returns the kernel to use for that step, in the form the entry would otherwise take. Use it when the shape of a kernel depends on shared pools, on the species' own state or on the environment, for example growth that slows under crowding:

:growing => responsive(ctx -> ((z′, z) -> survival(z) * growth(z′, z, ctx.pool.space)))

A dependence that only scales a kernel, by a number or by a factor for each trait value, is cheaper as an ordinary response; see respond and by_trait. A kernel that depends on one pool alone can be built once at chosen values of the pool and interpolated between them; see tabulated.

MatrixCommunityModels.tabulated — Method
tabulated(g; pool, grid, outside = :error)

Like responsive, a kernel of kernel_net whose shape changes from one time step to the next, but one that depends on the context only through the pool pool: g(x) returns the kernel (in the form the entry would otherwise take) when the pool holds x. Rather than being rebuilt every step, the kernel is built once at each value of grid (an increasing list), the first time that value is needed, and kept. Each step the pool's value x falls between two neighbouring grid values a ≤ x ≤ b, and the kernel used is the linear interpolation (1 - w) K(a) + w K(b), w = (x - a) / (b - a), entry by entry. At a grid value it is the kernel built there. This is how the R package matreex runs its forests (its grid is the whole basal areas).

A pool value outside the grid, x < first(grid) or x > last(grid), is handled according to outside:

  • :error (the default): throw a DomainError, so that the grid can be widened;
  • :clamp: use the kernel at the nearest end of the grid;
  • :exact: build the kernel at x for that step, as responsive would.

A pool value that is not a number (NaN) is always an error.

The interpolation error is of the order of the square of the grid spacing times the curvature of the kernel in x; with a growth kernel whose mean shifts with the pool, a spacing small against the width of the kernel keeps it small. The kernels are kept as the block of the projection matrix they fill, and only the band of each column that is not zero is stored, so a growth kernel that moves individuals a few cells takes much less memory than a dense block (the growth kernels of forest_tree on 700 cells take 0.2 to 0.9 MB per grid value, against 3.9 MB). The kept kernels are shared by every copy of the net and by every species built from it.

:growing => tabulated(ba -> ((z′, z) -> survival(z, ba) * growth(z′, z, ba)); pool = :basal_area, grid = 0:1:80)

MatrixCommunityModels.trait_weights — Method
trait_weights(stage, f; stratum = nothing)

Pool weights given as a function of the trait: each individual of stage with trait z contributes f(z). For the occupies argument of species:

species(:tree, net; occupies = [:basal_area => trait_weights(tree, d -> pi * (d / 2)^2)])

In a net made with stratify the weights apply to the individuals of every stratum. With stratum they apply to that stratum alone, so that a pool can hold, say, the infected individuals only:

species(:host, net; occupies = [:infectious => trait_weights(plant, z -> z^2; stratum = :infected)])
